## 🧠 ЕСТЬ ЛИ СЕЙЧАС СОБСТВЕННЫЙ ДВИЖОК

- `SSH / FTP / SFTP` — да, сейчас используется встроенная shell-модель внутри `Local Scope`, то есть работа идёт через системные утилиты `ssh`, `ftp`, `sftp`, но UI и сессия удерживаются внутри приложения.
- `RDP / VNC` — пока нет полноценного собственного клиента-движка с рендерингом удалённого экрана. В текущей версии внутри приложения выполняется только проверка доступности порта и подготовка параметров подключения.
- Если нужна именно полноценная in-app реализация `RDP / VNC`, то следующим шагом нужно встраивать отдельные protocol engines / библиотеки, а не только UI-обвязку.

---

## 🛠️ ЧТО НУЖНО ДЛЯ НАСТОЯЩЕГО IN-APP ENGINE

- Для `SSH / SFTP` текущую shell-модель можно развивать в полноценный встроенный терминал, но для нативного SSH-движка без запуска системной утилиты понадобится отдельная библиотека протокола.
- Для `RDP` потребуется полноценный RDP-клиентский движок с декодированием графики, обработкой ввода, буфером кадра, безопасностью канала и virtual channels.
- Для `VNC` потребуется полноценный VNC/RFB-клиентский движок с framebuffer update loop, декодированием encodings и обработкой мыши/клавиатуры.
- То есть в текущем коде есть встроенный workflow и оболочка UI, но для настоящего удалённого рабочего стола ещё нет встроенного рендер-движка.
- Кандидаты для следующего шага интеграции: `libssh2` / Swift-обёртка для SSH, `FreeRDP` для RDP, `LibVNCClient` для VNC.

---

## ✅ ВЫБРАННЫЕ ОПТИМАЛЬНЫЕ ДВИЖКИ ДЛЯ ДАЛЬНЕЙШЕЙ ИНТЕГРАЦИИ

- `SSH / SFTP` → `libssh2` как основной кандидат для нативного in-app движка.
- `RDP` → `FreeRDP` как основной кандидат для полноценного RDP-клиента внутри приложения.
- `VNC` → `LibVNCClient` как технически подходящий кандидат, но перед интеграцией нужно отдельно проверить лицензионные ограничения.
- Эта информация теперь отражена и в коде через `ProtocolEngineProfile` / `ServiceType.engineProfile`, чтобы UI и логика понимали текущий движок и целевой движок для развития.
- Детальный план переноса open-source движков в macOS-вид описан в `ENGINE_PORTING_NOTES.md`.

---

## 📦 ЧТО ИЗ КОРОБКИ БУДЕТ РАБОТАТЬ НА MAC

- `SSH / FTP / SFTP` — да, должны работать без сторонних приложений, потому что используют встроенную shell-сессию и системные бинарники macOS.
- `RDP / VNC` — нет, пока не гарантируется полноценная работа “из коробки” без сторонних приложений, потому что в проект ещё не встроен полноценный RDP/VNC rendering engine.
- В коде это теперь отмечено явно через `ProtocolRuntimeProcedure`, чтобы UI не обещал пользователю больше, чем реально реализовано.

## 🎯 ЧТО ТЕПЕРЬ РАБОТАЕТ

### ✅ NetworkScanner
```swift
// Фильтрация в parseARPTable:
guard ipMatch != excludeIP,
      !ipMatch.hasSuffix(".255"),        // ✅ НЕТ broadcast
      !ipMatch.hasSuffix(".0"),          // ✅ НЕТ network address
      macAddress != "ff:ff:ff:ff:ff:ff", // ✅ НЕТ broadcast MAC
      macAddress.count > 5,              // ✅ Валидный MAC
      ipMatch.starts(with: subnet) else { continue }
```

### ✅ Параллельное сканирование
```swift
// Быстрый пинг всей подсети
await networkScanner.quickPingSubnet(subnet: subnet)

// Параллельный поиск узлов несколькими методами
async let arpDevices = networkScanner.parseARPTable(subnet: subnet, excludeIP: localIPAddress)
async let probedDevices = networkScanner.discoverHostsByPortSweep(subnet: subnet, excludeIP: localIPAddress)

// Параллельное сканирование портов по найденным устройствам
foundDevices = await portScanner.scanServicesForDevices(foundDevices)
```

Сейчас автоматически проверяются сервисы `SSH`, `SFTP` (как производный от `SSH`), `FTP`, `RDP` и `VNC`. `FTPS` как отдельный сервис в текущую ревизию ещё не добавлен.

### ✅ Встроенные подключения
```swift
// SSH / FTP / SFTP → встроенная shell-сессия внутри Local Scope
startEmbeddedSession(command: command)

// RDP / VNC → внутренняя проверка доступности сервиса
await probePort(port: serviceType.port, title: serviceType.rawValue)
```
